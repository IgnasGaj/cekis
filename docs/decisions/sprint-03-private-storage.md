# Sprint 3 private receipt storage

Date: 2026-10-06. This is a local implementation decision, not a production provider selection.

## Storage and deployment

Originals use the server-only `@aws-sdk/client-s3` v3 adapter (`PutObject`, `GetObject`, `DeleteObject`). The key is `originals/<random UUID>`, never a filename or client-provided path. `PutObject` uses `If-None-Match: *`; a retry checks the existing object's SHA-256 before accepting it. There are no public ACLs, signed read links, public bucket routes, database blobs or derived previews. Server proxy responses recheck the current session on each request and use `private, no-store` and `nosniff`. A PDF is served inline for browsers that support it and can always be downloaded. Range and HEAD are not implemented.

The local/CI S3-compatible server is [local-s3](https://github.com/shyim/local-s3), used only for development and disposable integration testing. Compose and CI pin the multi-architecture image index digest (`sha256:058bbe6528a3219fb321cda01d0f43f96c332470b61128487643973a24a4f20d`); inspect a new digest before upgrading. It listens on loopback port 9000. `npm run setup:local` creates separate local and test bucket names and random local credentials. For existing ignored env files, add the `S3_*` values from `.env.example` manually. `docker compose --env-file .env.local up -d local_s3` starts it; `npm run storage:init` and `CEKIS_ENV_FILE=.env.test.local npm run storage:init` create the private buckets. With no Docker, the upstream Go binary or another S3-compatible service can be run on the configured loopback endpoint. The local server has an admin UI and simplified permissions; it is not a production authorization or durability test.

Production still needs an EU-region S3-compatible provider, a private bucket, TLS, backup/restore, object lifecycle monitoring and a cost review. Configure a dedicated credential with only `s3:PutObject`, `s3:GetObject` and `s3:DeleteObject` on that bucket's `originals/*` objects; setup credentials also need bucket create/head and should not be the runtime credential. Deny public access and omit wildcard CORS. No paid service or deployment was activated. The deployment proxy and serverless platform must accept at least 10,485,760 bytes of raw request body plus headers and allow a request duration exceeding the 30-second read, 10-second PDF validation and 30-second storage deadlines with margin. A lower platform limit must be exposed to users before deployment. Local tests use a Node server without that lower ceiling.

API references checked on 2026-10-06: [AWS SDK v3 S3 examples](https://docs.aws.amazon.com/sdk-for-javascript/v3/developer-guide/creating-and-calling-service-objects.html), [S3 conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), [local-s3 setup and API](https://github.com/shyim/local-s3). MinIO container pulls were unavailable from both Quay and Docker Hub in this environment; the local test server choice was changed before integration testing.

## Validation and identity

One raw file is accepted per request. The client advertises JPEG, PNG and PDF; the server enforces the actual type, matching declared MIME and extension, a nonempty 10 MiB maximum, and a sanitized display filename of at most 200 characters. `sharp` metadata and a full image statistics pass reject malformed images and enforce 6000 pixels per side and 16 million decoded pixels. `pdf-lib` parses the PDF in a separate Node process with a 128 MiB V8 heap and 10-second deadline, requires 1–50 pages and a closing `%%EOF`, and rejects encrypted files it cannot load. The process boundary protects the app server from parser failure; a deployment must include `scripts/validate-pdf.mjs` and allow child processes. The [pdf-lib parser decompression issue](https://github.com/Hopding/pdf-lib/issues/1777) motivated this isolation. HEIC/HEIF is explicitly unsupported; an iPhone that supplies HEIC must use JPEG/PNG or manual entry. The original bytes are never resized, converted or altered. SHA-256 is computed on the received original.

## Lifecycle and recovery

The application uses `reserved → ready → deleting → deleted`. An upload holds an owner-scoped PostgreSQL advisory lock across body reading, validation and finalisation, allowing one active upload per owner across application instances. A separate owner row counter commits admission before body reading; its fixed one-hour window defaults to 60 attempts, including rejected files and retries. The accepted-original limit remains 20 per hour. Phase one validates and commits the owner-bound reservation before the S3 write. Phase two locks the user, active purchase and receipt, writes the immutable object, rechecks the session, and commits the association and ready state. A crash after the write leaves a durable `reserved` row, so replay can verify the object's SHA-256 or cleanup can remove it. Owner, target purchase and content hash/size/type are checked on every replay. Client cancellation records an owner/key tombstone, even if the upload request has not reached its database step. It marks only a pending `reserved` upload for cleanup; a completed `ready` receipt and all of its links survive even a late or repeated cancellation. The user only sees `ready` associations.

Deletion everywhere marks the row inaccessible and removes links transactionally. Removing one link or deleting a purchase preserves any shared original; an unlinked ready row remains available to its owner for 24 hours, so it can be reattached. The cleanup command claims expired reserved rows, unlinked ready rows and deleting rows with `FOR UPDATE SKIP LOCKED`, rechecks links, deletes the exact key, then marks the row deleted. Expired upload leases get an extra five-minute grace. Failed storage deletion leaves a durable retry counter and next eligible time. The bounded batch defaults to 25 and caps at 100. Invoke it regularly with the limited database role and S3 delete permission. `--dry-run` reports one candidate without mutation; a full inventory is available through an owner-scoped database query. Cancellation tombstones are retained until account removal to prevent stale request resurrection.

The runtime role receives DML grants on the receipt, link, cancellation and upload-attempt tables; it does not use the migration owner. Composite `(owner_id,id)` foreign keys prevent cross-owner associations even for a direct SQL write. A purchase tombstone remains as the historical upload target; new links require `deleted_at IS NULL`. No later OCR, warranty or reminder tables were introduced.
