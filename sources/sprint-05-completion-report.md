## Data and calendar policy

Forward migration 0008 adds `purchase.warranty_state` (`unknown`, `none`, `known`), a PostgreSQL `date` end day, optional confirmed whole-month duration/source, and integer `revision`. Existing purchases become `unknown` with no end date or metadata. Sprint 4 had no stored confirmed warranty data to preserve. SQL checks reject unsupported state, contradictory nulls, missing known date, dates outside `0001-01-01` through `9999-12-31`, end dates before purchase dates, invalid source/duration and PostgreSQL infinity. The server also rejects future purchase dates, malformed calendar dates and unconfirmed or mismatched suggestions. The application duration limit is 1–600 whole months. Update timestamps remain timezone-aware.

The saved end date is inclusive. One `Europe/Vilnius` calendar date is derived per list response and passed to SQL filtering/ordering and rendered status. Civil-day subtraction avoids DST-hour arithmetic and viewer timezone shifts. Known dates before today display **Pasibaigė**; today through today plus 30 days inclusive display **Greitai baigsis**; later dates display **Galioja**. Day 0 reads **Baigiasi šiandien**; expired purchases show the saved end date without a negative countdown. `unknown` reads **Garantija nenurodyta**, while `none` reads **Pažymėta: garantijos nėra**. Duration suggestions add the whole number of months once and clamp the original purchase day to the last day of the target month. No statutory period or entitlement is implied.

The **Galioja** filter intentionally includes **Greitai baigsis**. Other filters select soon, expired, unknown or none separately. Filtering and sorting run in the owner-scoped PostgreSQL query before 50-item pagination and combine with product/seller search. **Pagal artimiausią garantijos pabaigą** orders unexpired known dates ascending, expired known dates by most recent expiry first, then unknown/none. Creation timestamp descending and ID descending break all ties. URL values are allowlisted and preserved through list/detail/edit navigation.

## Editing and access

Manual purchase entry, purchase editing, receipt-backed creation and OCR review include a compact warranty editor. New records start unknown with no duration or checked confirmation. A known date requires deliberate checkbox confirmation. Changing date, mode, duration or purchase date clears confirmation. When an existing known purchase date changes, the stored end day remains visible; a stored duration moves to direct-date review rather than silently computing a replacement. Changing to unknown/none clears obsolete metadata in the same save. Omitted warranty fields in ordinary purchase/review saves preserve stored warranty data; explicit changes are parsed as complete states. Deletion scrubs the warranty fields as part of the existing replay tombstone.

Purchase edits use an atomic expected-revision predicate. Receipt review checks the same revision under its existing owner-scoped purchase row lock and updates purchase and receipt number in one transaction. A stale edit returns a Lithuanian conflict without replacing newer fields; entered form values remain for review/reload. Exact receipt-review retries can acknowledge an already-applied identical result without another update. Owner identity comes from the authenticated session. Purchase, review and receipt queries are independently owner-scoped; no client owner ID, object key or computed status is trusted. The app database role retains DML access without schema creation rights.
