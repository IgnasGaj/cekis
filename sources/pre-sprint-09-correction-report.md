# Pre-Sprint 9 audit corrections

Date: 2026-10-09 (Europe/Vilnius). Base: `main` at `d88330e04b71f03c5df2c3957440ea3a42a1d7bf`. Source audit: [pre-sprint-09-project-audit.md](pre-sprint-09-project-audit.md).

## Scope and corrections

This is correction work only. Sprint 9, deployment, production data and paid services were outside scope. Existing 24-month warranty defaults, 6/12/24/36 choices, reminders, OCR suggestions, receipt originals and purchase-list pagination remain in place.

- **F1:** The review page submits the receipt number it originally displayed. Under the purchase and receipt row locks, the review route compares that snapshot with the current shared number. A stale change returns HTTP 409 with Lithuanian reload/review guidance, and the client leaves entered purchase values in the form. An unchanged-number replay remains idempotent. Older clients without a receipt snapshot may replay an unchanged number but cannot change shared metadata. No schema migration was needed.
- **F2:** Both the existing-receipt picker and the attached-receipt list use bounded 50-row pages with a continuation cursor. Queries remain owner-scoped, order by timestamp then receipt ID, and validate cursor input. Repeated filenames show the upload date and an ID prefix, without object keys. There is no attachment cap.
- **F3:** The PDF manual review browser case now records the POST response status and submitted product value before asserting navigation, then checks the committed product value and reopens the detail. The whole review fieldset is disabled until hydration, so edits and submission cannot occur before React controls the form. After a successful POST the page uses a full navigation to the purchase detail. The persistence and navigation assertions remain; retries and timeouts were not increased.
- **F4:** Receipt link and cancellation mutations validate a non-null JSON object before reading fields. Null, arrays, strings, malformed JSON and missing or wrong-type IDs return controlled 4xx responses before a database mutation.
- **F5:** The repository owner account had admin permission. GitHub's default branch was changed from `feature/sprint-01-authentication-app-shell` to `main`; `git ls-remote --symref origin HEAD` and a fresh default clone both selected `main` at the audited baseline SHA. No branch was deleted or protection bypassed.
- **F6:** README now describes the implemented warranty choices and automatic image scanning. Sprint 7 and 8 completion reports record the exact audited-main CI result, including the OCR retry.

## Focused regression evidence

Disposable PostgreSQL and Chromium cases passed for two purchase reviews of one shared receipt, an unchanged replay, purchase values retained on conflict, 51 same-name eligible receipts, 101 attachments, owner-scoped cursor validation, and malformed mutation bodies. The pre-correction OCR case passed three retry-disabled local runs, which did not reproduce the one flaky attempt seen in [audited-main CI 37824588095](https://github.com/IgnasGaj/cekis/actions/runs/37824588095). After the correction, that case passed twice with retries disabled; each run observed an HTTP 200 save response, reached the expected detail URL, confirmed the stored product value, and reopened it. Initial test fixture failures were strict matching of Next's empty route announcer, an immediate database read before an asynchronous link completed, and an attempted response-body read after full navigation; those assertions were corrected without relaxing application checks.

The first full local browser run after implementation reported 53 passes and one failure with retries disabled. The new receipt-list remount caused the existing uploaded-receipt review link to disappear during `router.refresh()`. The manager now keeps its uploader mounted and treats changed first-page signatures as a fresh pagination base. The affected upload/review and 51/101 pagination cases both passed afterward. The final full run is the acceptance gate, so this regression is not hidden as a flaky pass.

The first pushed candidate `38f589fe850c9f40fa4b0532769c39643327b92e` passed [PR CI run 37902643224](https://github.com/IgnasGaj/cekis/actions/runs/37902643224), but Chromium reported **53 first-attempt passes and one flaky retry pass** in the OCR review case. The affected test then passed three local runs with retries disabled; lint and typecheck passed. The first candidate's green conclusion is not treated as correction acceptance; a fresh exact-head CI result is required.
